### 1. readme（agent-org README，v0.1.28）
- 重點：一句話定位：PM、架構師、工程師、審查委員會、QA、Release 各是一個子代理，只靠文件交接，負責人只在三個關卡簽核，被擋下的地方累積成跨專案的組織記憶。
- 重點：指令：/agent-org:ship、status、audit、direct、setup、help。
- 重點：「規則由程式執行」：org.py 帳本檢查階段推進、hook 擋越權寫檔、決策信只能回一次。
- 重點：明寫「做不到的」：擋的是忘記和走捷徑，不是蓄意造假。
- 建議頁面：overview、enforcement、commands。
- 不確定：安裝步驟（私人 repo 的 git clone）要不要寫進 Wiki。

### 2. design-doc（設計文件 artifact）
- 重點：組織架構圖：你 → 主持人 → 六個部門；知識管理員與組織監察人在派工線之外。
- 重點：九階段流程與 S／M／L 分級，三個關卡 A（值得做嗎）、B（選方案）、C（怎麼落地）。
- 重點：組織記憶三步驟：記錄（episodes）→ 提煉（知識管理員）→ 讀取（派工 brief）；「每個角色從下游學」。
- 重點：版本演進：11/05 設計 → plugin → 參考 Paperclip 改成程式強制 → 0.1.28。
- 建議頁面：dev-flow、tiers、gates、org-memory、auditor、version-history。
- 不確定：設計文件很長，「向 Paperclip 借了什麼」「維運」兩節要不要收。

### 3. ship-skill（主持人流程）
- 重點：主持人不寫程式、不審程式、不投票、不軟化結論。
- 重點：派工機制：先用 org.py 組知識 brief，再寫任務 brief，一份 brief 一個子代理，同一波平行派出。
- 重點：退回規則：⑥⑦ 任何 BLOCK/VETO/FAIL 回到實作；第三次退回改派升級處理；安全否決不能被抵銷。
- 建議頁面：orchestrator、review-and-bounce。
- 不確定：指令細節（org.py 子指令）要寫到多細。

### 4. roles（13 個角色定義與 models.yml）
- 重點：每個角色的職責、能用的工具、產出檔案；都看不到負責人的對話。
- 重點：模型分配：PM／架構師／審查用 Opus，工程師／QA 用 Sonnet，Release 用 Haiku，L 級架構與升級用 Fable；審查者和工程師刻意用不同模型。
- 建議頁面：roles（含模型表）。
- 不確定：每個角色要不要各開一頁，還是一頁表格。

### 5. review-plan-1117（11-17 最終審查計畫）
- 重點：使用者逐項確認後發現有幾條同意過的設計被實作改掉或漏做（等待時先做別的事、教訓固定門檻），計畫要補回。
- 重點：Slack 通報設計、影子試跑、三台機器實機測試、用組織重做 Clawd。
- 建議頁面：design-evolution（設計與實作的落差與修正）。
- 不確定：這份是計畫不是結果，內容是否都已實作要另外確認，Wiki 只寫「計畫」。

### 6. clawd-run（實際 run：Clawd 每日用量熱力圖，11/10–11，L 級）
- 重點：完整走過分級→PRD→關卡 A→設計→設計審查→關卡 B→拆任務→實作→審查→QA→關卡 C→發版→回顧。
- 重點：設計被維護者 BLOCK 一次（拆工循環依賴、帳本格式沒有演進規則），第二輪三位審查都 PASS，之後 code review、QA 一次通過。
- 重點：回顧產生 4 條教訓（L-0001～L-0004），其中 3 條經負責人同意升到通用層。
- 重點：回顧指出記錄缺口：「逐項 BLOCK」不會被自動記成事件。
- 建議頁面：case-clawd-heatmap（實例）、連到 org-memory、review-and-bounce。
- 不確定：設計細節（Swift、帳本格式）要寫多少，還是只寫流程。
