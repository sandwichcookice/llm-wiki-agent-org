agent-org 是什麼？

一個 Claude Code plugin：把公司的軟體開發流程搬進 Claude Code。

  • 每個職位是一個 AI 子代理
  • 角色之間只靠文件交接
  • 人只在三個關卡簽核
生活化例子就像開一間小型軟體公司，只是員工全是 AI，你是老闆。

動機

為什麼不讓一個 AI 包辦？

  • 作者原本在試投票式的 court skill，看完後問：「為什麼我們不設計成正常公司的架構呢?」
  • 他也要組織會記住哪些地方被擋下來過，像 RAG 或 LLM Wiki 那樣持久化
  • 因此有三個核心想法：分工、人只在關鍵點出手、規則由程式執行
生活化例子一個人又寫作業又自己批改，很容易放過自己的錯；分給不同的人寫和改，錯誤比較容易被抓到。

組織

主持人：只派工，不動手

  • 主持人就是你開的主 session，下 /agent-org:ship 後開始分級、派工、記帳
  • 不寫程式、不審程式、不投票，也不軟化審查結論
  • 派工時只給 brief：要讀哪些檔、做什麼、寫到哪裡；子代理每次都是全新的上下文
  • 遇到問題要問負責人，不要自己猜
生活化例子像專案經理：不親自寫程式，但確保每個人拿到正確的文件、按順序交棒。

流程

一件工作的九個階段

① 需求 PM關卡 A② 設計③ 設計審查關卡 B④ 拆解⑤ 實作⑥ Code Review⑦ 測試關卡 C⑧ 發佈⑨ 回顧
  • 每個階段留下一份文件，下一階段就讀那份文件
  • 推進前 org.py 先檢查文件在不在、審查是不是 PASS
生活化例子像接力賽：每一棒交的是一份文件，而不是口頭交代。

流程

依大小決定流程長度

分級什麼情況關卡子代理
S 小改改字、小 bug、單一檔案C約 2
M 一般功能單一功能，不動 API 與資料模型B、C約 5
L 大型或高風險新模組、API／資料模型變更、安全相關A、B、C10 以上

拿不準時往大的那一級算；專案第一個 run 不會是 S。

生活化例子公司也不會為了改一個錯字寫設計文件。

人在哪裡

你只在三個關卡出手

  • 關卡 A：值得做嗎？　關卡 B：選哪個設計方案？　關卡 C：怎麼落地？
  • 主持人先寫決策信（問題、選項、建議），你回覆後 org.py 才放行
  • 決策信一封只能回一次；不可逆的信不會逾時自動照做
  • 關卡 C 不只是合併，也可以選開 PR 或照你的指示做
生活化例子像主管簽公文：平常不用管細節，只在關鍵的公文上簽名。

品質

沒過就退回，第三次升級

  • 審查者彼此看不到對方結論，各自回「通過」或「阻擋」
  • 設計審查沒過 → 回設計；Code Review 或測試沒過 → 回實作，後面全部重做
  • 同一關第三次退回 → 改由升級處理（Fable）重做，還不過才交給你
  • 安全否決不能被別人的通過抵銷
生活化例子Clawd 熱力圖那次，設計第一輪被維護者擋下，修好後三位審查都通過。

記憶

越做越聰明：組織記憶

① 記錄：被擋的事件→② 提煉：知識管理員寫成教訓→③ 讀取：派工時放進 brief
  • 每個角色從下游學：被擋的一方記「不能這樣做」，放行卻漏抓的審查者也要記
  • 教訓會冷藏、升級到跨專案層，甚至變成程式自動檢查
生活化例子就像錯題本：考試錯過的題目寫下來，下次考前先翻一遍。

強制

規則由程式擋住

  • 作者第一天就問：要怎麼確保 Claude Code 真的照架構跑？
  • org.py 帳本：文件不在、審查不是 PASS、關卡沒放行，就推不過去
  • hook：審查檔只有該角色能寫，主 session 不能代寫
  • 也老實寫出擋不住的：刻意用 Bash 寫檔、審查者有沒有真的看
生活化例子像門禁卡：不是貼公告請大家別進，而是沒卡就刷不開。
本頁依據 Wiki：enforcement
治理

誰來檢查組織本身？

  • 組織監察人：不屬於任何專案，只看組織運作得好不好
  • 只能提建議，不能改任何東西
  • 建議要過三道關：引用指標、你用決策信決定、兩期後看指標有沒有變好
  • 不能削弱底線，例如安全否決不能被抵銷
生活化例子像公司的監察人：不參與經營，只對組織提出改進建議。
