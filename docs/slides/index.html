agent-org 是什麼？

  • 一個 Claude Code plugin，把公司的軟體開發流程搬進 Claude Code
  • 每個職位由一個 AI 擔任，角色之間只靠文件交接
  • 使用它的人（以下稱負責人）只在三個關卡簽核
生活化例子就像開一間小型軟體公司，員工全是 AI，你是老闆。

先認識幾個詞

名詞小辭典

  • 關卡：負責人唯一要出手、簽核後才能往下走的地方，共 A、B、C 三個
  • 分級：主持人先依改動大小分成 S／M／L，決定要跑哪些階段
  • 子代理：每個職位是一個子代理，每次被叫起來都是全新的上下文，看不到負責人的對話
  • brief：派工時給子代理的文件：角色指令、專案目標、常駐清單、這次的任務、相關教訓
  • run：交給組織的一件任務，從分級開始，到完成結束
  • PRD：產品經理（PM）寫的需求文件，內容是問題、使用者、驗收條件
  • org.py：記帳工具，負責組 brief、記事件、檢查階段推進、處理決策信
  • hook：掛在 Claude Code 上的自動檢查，例如每次使用工具前檢查權限
  • worktree：替每個工程師開的獨立資料夾，各自一個分支，互不干擾
  • PASS／BLOCK／VETO：審查結論；BLOCK 是阻擋，VETO 是安全審查的否決
  • Fable／Opus／Sonnet／Haiku：四種 Claude 模型；依定價 Fable 最貴、Haiku 最便宜

動機

為什麼不讓一個 AI 包辦？

  • 作者原本在試投票式的 court skill，看完後問：「為什麼我們不設計成正常公司的架構呢?」
  • 他也要組織會記住被擋下來過的地方，「像是RAG或是LLM wiki那種」
  • 三個核心想法：分工、人只在關鍵點出手、規則由程式執行
生活化例子一個人又寫作業又自己批改，很容易放過自己的錯；分給不同的人寫和改，錯誤比較容易被抓到。

組織

組織裡有誰

共 13 個角色，每個都是一個子代理：

  • PM 寫 PRD；架構師做設計文件、拆任務
  • 多位工程師各自在 worktree 實作一個任務
  • 審查：Code Reviewer 看 diff 與設計；安全審查可以否決（VETO）
  • QA 依 PRD 驗收條件測試；Release 寫發佈清單與回滾方案
  • 知識管理員在回顧時把被擋的原因寫成教訓
  • 審查者和工程師刻意用不同模型，降低「同一個模型自己說自己好」
本頁依據 Wiki：roles
組織

主持人：只派工，不動手

  • 主持人就是你開的那個主 session，下 /agent-org:ship 後開始分級、派工、記帳
  • 不寫程式、不審程式、不投票，也不軟化審查結論；hook 會擋它改專案檔案
  • 派工只給 brief，一個子代理做一件事
  • 作者的要求：「有遇到執行問題請問我 不要自己猜測」
生活化例子像專案經理：不親自寫程式，但確保每個人拿到正確的文件、按順序交棒。

流程

大型任務的九個階段

① 需求關卡 A② 設計③ 設計審查關卡 B④ 拆解⑤ 實作⑥ Code Review⑦ 測試關卡 C⑧ 發佈⑨ 回顧
  • 這是 L 級（大型）任務的完整路徑：九個階段、三個關卡
  • 每個階段留下一份文件，下一個階段就讀那份文件
  • 推進前，org.py 先檢查文件在不在、審查是不是 PASS
生活化例子像接力賽：每一棒交的是一份文件，而不是口頭交代。
本頁依據 Wiki：dev-flow
流程

依大小決定流程長度

  • S 小改（改字、小 bug、單一檔案）：只跑實作、Code Review、測試，關卡只有 C，約 2 個子代理
  • M 一般功能（不動 API 與資料模型）：關卡 B、C，約 5 個子代理
  • L 大型或高風險（新模組、資料模型變更、安全相關）：全部九個階段，10 個以上子代理
  • 拿不準時往大的那一級算；專案的第一個 run 不會是 S
生活化例子公司也不會為了改一個錯字寫設計文件。

人在哪裡

負責人只在三個關卡出手

  • 關卡 A：值得做嗎？　關卡 B：選哪個設計方案？　關卡 C：怎麼落地？
  • 主持人先寫決策信（問題、選項、建議），負責人回覆後 org.py 才放行
  • 決策信一封只能回一次；不可逆的信不會逾時自動照做
  • 關卡 C 不只是合併：作者加了「開 PR」和細部實作的選項
生活化例子像主管簽公文：平常不用管細節，只在關鍵的公文上簽名。
本頁依據 Wiki：gates
品質

沒過就退回，第三次升級

  • 審查者彼此看不到對方的結論，各自回「通過」或「阻擋」
  • 設計審查沒過 → 回設計；Code Review 或測試沒過 → 回實作，後面全部重做
  • 同一關第三次退回，改由升級處理（Fable 5.2）重做；還不過才交給負責人
  • 安全的 VETO 不能被其他人的 PASS 抵銷
生活化例子Clawd 熱力圖那次：設計第一輪被維護者擋下（拆工有循環依賴、帳本格式沒有演進規則），修好後三位審查都通過。

記憶

越做越聰明：組織記憶

① 記錄被擋的事件→② 知識管理員寫成教訓→③ 派工時放進 brief
  • 記憶屬於組織、不屬於任何專案，放在 ~/agent-org/
  • 每個角色從下游學：被擋的一方記「不能這樣做」，放行卻漏抓的審查者也要記
  • 少了讀取這一步，它就只是一個沒人看的資料夾
  • 教訓會冷藏、升級到跨專案層，甚至變成程式自動檢查
生活化例子就像錯題本：考試錯過的題目寫下來，下次考前先翻一遍。
本頁依據 Wiki：org-memory
強制

規則由程式擋住

  • 作者第一天就問：要怎麼確保 Claude Code 真的照架構跑？
  • org.py：文件不在、審查第一行不是 PASS、關卡沒放行，就推不過去
  • hook：審查檔只有該角色能寫，主 session 不能代寫
  • 也老實寫出擋不住的：防的是忘記和走捷徑，不是蓄意造假
生活化例子像門禁卡：不是貼公告請大家別進，而是沒卡就刷不開。
本頁依據 Wiki：enforcement
治理

誰來檢查組織本身？

  • 組織監察人：不屬於任何專案，只看組織運作得好不好，只能提建議
  • 作者的原話：「我需要多一個組織負責人（類似股東） 獨立於整個專案」
  • 建議要引用指標，由負責人用決策信決定，改完兩次監察後看指標有沒有變好
  • 不能削弱底線，例如安全否決不能被抵銷
生活化例子像公司裡不參與經營的監察人。

複習

小測驗與總結

  • Q1 主持人會自己寫程式嗎？　答：不會，hook 會擋它改專案檔案
  • Q2 負責人在哪裡出手？　答：關卡 A、B、C
  • Q3 被擋下的經驗會去哪裡？　答：寫成教訓，下次派工放進 brief
